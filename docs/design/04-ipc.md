# IPC、请求与共享通道

[设计总览](00-overview.md) · [实现状态](../status.md) · [执行与验收](#执行与验收)

状态：2026-11-16可信Rq预付/队列/取消收尾状态机已局部实现并通过双架构QEMU；原生IPC授权、阻塞/事件及资源回复仍待实现，见末尾/status，不称完整IPC、性能或CI验收。

## 同步 RPC

第一版直接向获授权的目标进程调用，不设独立 Endpoint 对象。
一个进程是一个接收者；每执行上下文最多一个同步等待，可有编译配置限定的异步及收尾请求。
首版操作：call、send、recv、reply、reply_recv。send 为同步单向发送，异步提示仍使用事件位。
服务可接收并暂存多个 CALL，在有结果时按请求标识回复；暂存数量有明确上限。服务仍可同步调用下游：init → fs → blk。
回复关系存于预付的请求记录，不作为可复制资源暴露；请求在终结、服务收尾、调用者结果消费及跟踪释放完成后才可复用。
只有接收该 CALL 的服务能回复对应请求标识；标识不可委派，成功回复后失效。调用者死亡后旧回复不得投向复用后的进程。
目标死亡取消排队及等待回复的客户端；每次重建均产生新身份，旧句柄不得静默指向新服务。

### CALL授权绑定目标镜像（语义收口）

本地CALL/SEND授权除操作权限外，固定目标完整实例及目标镜像代次，不只保存槽或PID。目标exec后旧入口失效，不能因Life/PID仍在而投向新程序；重启新实例同样须重新授权。引导期可为未启动服务建立初始镜像入口，但不能向未发布实例无限排队，状态错误随ABI冻结。

| 时点 | 行为 |
| --- | --- |
| 新call/send提交 | 核对本地授权、目标完整身份/镜像、可接收状态，再建立等待，不按当前同PID重定向 |
| 已排队而目标exec/退出 | 终结旧镜像等待，未交付请求不由新镜像接收 |
| 已接收而目标exec/退出 | 业务可能已执行，按旧接收镜像取消/收尾，不能声称未执行或自动重放 |
| 新镜像使用旧REQUEST | 按接收者实例/镜像拒绝，不能回复或rqfinish旧镜像请求 |
| free旧CALL授权 | 可解除自己的引用，不要求旧目标仍存活，避免失效入口无法释放 |

检查使用已持有的稳定Life/目标关联及镜像值，不为每次RPC添加跨服务查询；最终入队/交付与目标镜像切换原子排序。Rq固定两端原实例/镜像及引用，清理不从当前槽猜身份。客户端显式重建连接，不把旧授权原地改绑新服务。

资源reply交付后端CALL权须核验源入口目标镜像有效；检查后目标立即退出可以使新入口立即失效，授予成功不承诺后端永远在线。READY仍由init发布策略管理，内核不解析服务业务就绪。

客户端自身exec可按继承协议取得指向同一服务镜像的新本地入口，但旧会话须按source/image交接，不复活旧客户端Rq；目标服务exec则使旧入口不能用于新提交，不因保留fd而豁免。notify采用相同用户目标镜像边界；IRQ绑定仍按专门停机/解绑协议，不因镜像失效就自动完成设备收尾。

#### 示例：FS同PID执行新程序

A的入口绑定FS实例P/镜像3。P成功exec到4后，A以旧入口call失败，不能把旧FS协议送入新程序；已经交付的WRITE可能已生效，不能自动再写一次。A可free旧入口，再按明确服务发布取得新入口并建立新会话；旧fd不透明重开。

### 消息与返回元数据（已确定）

短消息固定为 `Msg { uint64_t words[4]; }`，共 32 字节；普通消息字含义由服务协议定义，内核不解析操作码。显式单资源回复方案例外：由内核标记格式并写入words[0]的新Handle，见后文。
大数据经预建立共享区传输；ARM64/RV64 的短消息优先通过寄存器传递，C 包装可以使用 Msg 指针而不要求内核复制用户结构。
接收元数据独立于用户消息：kind（CALL/SEND/EVENT）、source（内核确认的进程身份）、image（source的镜像代次）、request（CALL 回复标识）。image的额外返回寄存器见ABI方案，不占四个消息字。
SEND/EVENT 的 request 无效；EVENT 的 source 不伪装为用户进程，使用无效进程标识，事件位图在 words 中返回。
用户不能伪造这些元数据。无效 Handle 使用已确定的 0。

### source 与镜像身份（ABI方案）

服务会话绑定完整source实例及image，不能只用PID区分exec前后。CALL/SEND在提交时固定source/image，接收时返回该身份，不以接收时该PID的当前镜像替代；延迟回复和服务清理继续引用原身份。普通EVENT、普通/资源回复及不含接收来源的返回，image均为0，不能残留上一次接收值。

方案在已有寄存器结果之外使用RV64 t0、ARM64 x9返回u64 image，保持Msg四字和现有source/request位置。用户包装将其声明为显式输出/破坏寄存器，其他原有用户现场保存规则继续有效。这样接收端可直接核验每次数据请求的实例/镜像，不为热路径逐次调用身份查询。具体Trapframe/桩布局及编译约束须与共享ABI一起冻结，不能只改C结果结构。

受权生命周期登记仍凭真实REQUEST/构造关系取得内核引用，不能凭用户缓存的source/image两个整数扩大观察权限。普通SEND不产生可持有REQUEST，收到其身份元数据不自动获得对方长期观察授权。

#### 示例：同PID的新程序不能使用旧会话

A镜像7建立TTY会话，随后exec为镜像9。镜像9即使知道旧会话号，向TTY请求时内核返回source=A/image=9，TTY按会话的image=7拒绝，不等待终结提示送达才隔离。旧请求的迟到完成仍归7；生命周期通知负责最终清理，逐请求身份检查负责即时访问边界。
内核通信返回状态与服务回复内容分离：文件不存在等业务错误由服务回复，目标退出等通信错误由内核返回。
未来 RV32 可使用不同传输 ABI，保持 64 位字段和协议语义，不承诺所有架构均全寄存器传输。

寄存器布局见 [系统调用 ABI](06-abi.md)。

### 有界请求、异步与延迟接收（修订后）

每个请求使用独立 Rq 记录：双方完整身份、授权来源、消息、状态、结果和取消/收尾标志。
call 默认同步；CALL_ASYNC 提交成功后返回调用者侧 RPC Handle，不等对端完成。服务 recv 获不同类别的 REQUEST Handle。
rqpoll 查询结果，rqwait 等待，rqcancel 请求取消，rqack 确认消费；完成事件可合并，结果保留到确认，跟踪记录保留到服务收尾且调用者释放。
这些为明确 syscall，不使用通用 invoke；编号见06。同步call正常返回由内核代消费；捕获信号只退出等待并返回原RPC，后续显式查询/确认，强制终结未收尾记录仍由运行库/生命周期清理管理。
所有请求槽在进程创建时从固定池预付，耗尽返回资源不足，既不无限扩表也不分配内核堆。
recv 返回的 CALL 先占唯一即时分发名额；服务必须 reply 或 defer 后再 recv。defer 只占长期配额，最后一个分发名额不可借用。
CALL_ASYNC 接收前同样遵循目标 FIFO；SEND 无回复和长持有期，先前语义不变。
保留请求记录会增加有界元数据，换取取消、信号及响应式控制路径的完整生命周期，不再承诺“全系统每进程恰好一个请求”。

### 内部链表（已确定）

采用 Linux list.h 风格的侵入式循环双向链表，自行实现精简公共 include/list.h，不直接引入 Linux 全套依赖。
节点类型 List 含 prev/next 指针，哨兵节点作为表头；内部节点指针不作为用户 ABI 暴露。
首版操作包括初始化、判空、头尾插入、摘除、移动和可摘除遍历，内部函数遵循 listinit/listdel 等小写连写风格。
不同关系使用不同嵌入节点：Rq.queue 表示等待接收，Rq.owned 表示接收服务持有；同一节点禁止同时挂入多个表。
Handle 仍按全局表索引与代次校验，链表不承担身份/权限检查，也不替代引用与账目。
对象回收前必须摘除所有节点；摘除后节点恢复独立状态，DEBUG 检查重复入链及不合法摘链，安全遍历先保存下一节点。
等待/持有关系的迁移由 IPC 状态转换控制，不能因为 listdel 可重复调用就忽略重复完成或错误归属。
64 位双指针节点通常 16 字节，多个节点的实际开销纳入配置报告；不声称比索引链表一定更省或更快。
伙伴空闲块仍可使用页索引，避免为物理页元数据强制增加双指针；按场景选择，不强迫所有结构统一为 List。

Rq 的 queue 只在等待接收时挂入目标 FIFO，owned 只在已接收或取消收尾时挂入接收服务持有表。
接收在同一临界区内检查容量、摘 queue、挂 owned、提交状态并交付，不留下无负责者的中间状态。
排队取消摘 queue；接收后协作取消保持ACCEPTED/owned直至reply，强制终结才按DRAINING等待rqfinish/reply；结果已提交后不能因晚到取消重写成功。
回复/收尾校验归属及阶段，保存结果/收尾标志后摘 owned，再通知调用者并检查回收条件。
defer 只迁移即时/长期配额归属，沿用 owned，以标志区分，不额外增加 defer 链表。
服务退出先停止新交付，再分批清理等待/持有表；回收前全部节点独立，下游内存引用不随摘链自动释放。
每个已提交未收尾请求都属于等待队列或接收服务；可回收请求不能仍挂链，节点归属必须与状态机一致。

### 同步等待环（检测范围收口）

每线程至多保存一条当前有效的强IPC等待边，绑定目标完整实例/镜像及请求。首轮单线程进程与线程一一对应，不为每个排队请求都添加进程阻塞边。边表示“该线程现在必须等这个接收服务才能继续”，不是所有业务引用的依赖图。

| 操作/状态 | 是否建边 |
| --- | --- |
| 同步call等待回复 | 是，指向该Rq目标服务镜像 |
| 同步send等待接收 | 是，交付成功即清除 |
| CALL_ASYNC提交、rqpoll、已满足的rqwait | 否，不阻塞当前线程 |
| rqwait等待未终结结果 | 是，指向原接收服务镜像，不能用异步提交绕过环检测后再阻塞 |
| RQ_FINISH等待尚存活原服务收尾 | 是，服务仍为明确直接完成者时采用同一边 |
| 已死亡服务的管理/下游清理等待 | 不虚构指向死服务的强边；单独标记清理等待，依赖管理/外部进展 |
| recv/事件/闹钟等待、父wait、业务条件 | 不纳入这版单目标IPC环检测，不能宣称无环就不会死锁 |

在实际阻塞之前，先原子检查结果是否已经满足；未满足时沿目标当前强边遍历，回到调用线程则拒绝这次等待。遍历与登记在同一短IRQ保护段完成，不做内存分配，不持该保护等待服务。目标recv本身无出站边；有消息可直接交付时不为无须阻塞的路径制造边。

遍历使用编译配置CONFIG_WAIT_DEPTH上限，范围1..CONFIG_MAX_PROCS，默认值在容量规格冻结。超过深度且未证明有环时返回明确的等待检查限制错误，不伪报已发现死锁，也不能未经检查直接挂边；异步提交/有界查询可继续由服务协议选择。需要保证的最长IRQ屏蔽时间包含该最大遍历，不能只检查每个节点操作常数时间。

回复、发送交付、排队取消、中断退栈、退出及等待转移结束相应等待时清除匹配原边；仅置cancel_requested不能撤销其他仍有效的等待边；查到旧实例/镜像或已不匹配等待的关联不能沿当前复用槽继续。STOP保持独立暂停原因，不把实际等待边随意清掉；CONT后检查真实结果。handler递送前被中断syscall已经退栈并解除原边，外层Rq仍在排队、执行或强制终结收尾，不等于当前线程仍等待它；handler自己的阻塞调用重新建立当前边。

父wait、任意子/组等待、接收任意消息、条件变量及死亡服务清理可能依赖多个参与者，这版不扩成通用等待图。诊断须显示实际等待种类，不能把未覆盖关系显示为“没有依赖”。基础服务正常I/O仍避免同步回调调用链上的上游；检测只能拒绝可见强IPC环，不能保证遗漏回复、设备失联或业务协议有进展。

#### 示例：异步提交后立即等待自己

A向自己CALL_ASYNC可提交，因为尚未阻塞；A随后rqwait同一未终结请求，目标就是自身，环检测拒绝等待。A应通过正常接收/事件循环处理该请求，而不是以为异步提交意味着随后任何等待都安全。

#### 示例：A→FS→BLK→A

A同步等FS，FS同步等BLK；BLK再同步调用A时形成回到BLK的链并拒绝第三次等待。若BLK只是异步提交而继续运行，不形成这条强边；它自己的协议仍须保证后续结果能被处理，内核不替它证明业务无环。

### 同步 send（已纳入首版）

`send(target, message)` 使用与 call 相同的目标句柄、发送授权和固定长度消息格式。
接收者收到消息后发送者返回成功，不等待业务处理结果，不产生回复关系。
没有接收者时发送者阻塞；消息保存在发送者进程的出站记录中，不新建异步缓冲池。
同步 send/call 使用当前执行上下文的预付请求槽并进入目标 FIFO 队列；被取消旧操作用独立记录收尾，不覆盖新操作。
接收者必须从内核返回的消息种类区分 SEND、CALL 与 EVENT，用户消息不能伪造该元数据。
仅 CALL 建立按请求标识索引的回复关系，SEND 不占用回复记录；对 SEND 不能执行回复。
reply/reply_recv 必须校验请求标识和接收者身份，不得伪造回复；接收 SEND 后可通过 recv 继续接收。

成功只表示消息已交付，不表示业务操作已执行或持久化；业务确认应使用 call。
发送者进入就绪态前必须完成消息复制；目标在交付前退出则 send 失败，交付后退出不追溯改变成功结果。
发送者排队时退出须摘除队列节点；已交付消息是独立快照，不因发送者退出而失效。
发送授权撤销按[权限与资源](03-process.md)执行：未接收消息取消，已交付消息不追溯取消。
send 不解决服务持有 CALL 时不能接收其他请求的问题，也可能形成同步等待环。

#### SEND与Rq的统一方式

SEND复用当前上下文预付Rq作为排队/交付记录，不额外创建回复对象，也不向任何一端暴露RPC/REQUEST Handle。内核以消息种类区分：CALL接收后进入ACCEPTED并挂owned，SEND接收则完整复制四字及source/image到接收现场后直接TERMINAL成功，server_finished=true，不进入owned、不占未回复CALL名额。已有即时CALL未处理时的recv限制仍按接收契约执行，不借SEND绕开它。

| 先发生的动作 | SEND结果及记录 |
| --- | --- |
| recv完成交付 | 固定成功，摘queue，发送者可继续；接收者无需reply/rqfinish |
| 排队时信号取消/授权撤销 | 固定未交付失败，摘queue，不存在服务排空责任 |
| 目标退出/镜像变化先于交付 | 固定目标失效失败，不向新镜像重定向 |
| 发送者死亡先于交付 | 摘queue并完成本地退出清理，不留下服务回复义务 |
| 交付后任一端终止 | 不追溯改写交付成功；尚未回用户态的发送者按自身退出/信号规则处理 |

SEND不接受CALL_ASYNC、资源接收或服务延迟回复选项；输入错误在入队前拒绝。其取消结果不产生客户端RPC收尾Handle，因为尚未交付时已经摘队，已交付时消息已经独立复制且没有借用期。定时/其他事件提示仍使用notify，不把SEND改成隐式异步队列。

#### SEND不承诺共享数据已使用完

交付成功只保证四个消息字及内核来源元数据已复制。若消息指向双方已有共享环，缓冲可否复用由共享协议的生产/消费位置决定；不能因为send返回就覆盖对端尚未消费的数据。需要“服务处理完并归还本次槽”的交互应使用CALL及既定reply/rqfinish收尾。首轮SEND不传用户裸指针、不承担隐式共享区借用或资源交付。

#### 同步续点与记录回收

同步CALL/SEND等待的内核C续点会再次读取本次结果，因此除了三项回收责任，还必须保持该续点的临时记录引用。正常唤醒在读取/保存结果后解除；KILL走仅内核清理路径解除，不得因死亡代为置消费/释放位就先复用Rq，再让旧续点读取同槽新消息。这个唯一等待者引用属于已预付上下文与Rq关系，不新增公开对象；具体字段与池回收断言随布局冻结。

#### 示例：send之后共享环仍不可覆盖

serial先把字节发布到与tty的共享环，再send一个控制消息。send成功后只能知道tty已经收到控制字；环中尚未推进消费者位置的数据仍不能被serial覆盖。普通高频到达提示优先用合并notify，环的持久位置决定还有多少数据，不按SEND次数推算消费完成。

### recv 的选择与唤醒（已确定）

每次返回一条 CALL/SEND 消息，或一份合并事件位图；两类结果明确区分。
仅一类可用时直接交付，两类都可用时在消息和事件之间交替选择，避免任一类持续饥饿。
普通消息保持 FIFO，但长期延迟请求不能占用最后一个即时分发名额。recv 总能检查下一条新消息：立即回复/拒绝，或成功 defer 后再接收。
长期容量满时普通新请求由服务返回 BUSY，不能以不接收队头阻塞其后的 close/控制请求；事件另行交替处理。
检查消息/事件、登记等待和切换必须作为同一内核临界区完成，不允许检查与睡眠之间丢唤醒。
服务若使用同步下游 call/send，普通事件只置 pending、不打断等待；需要响应控制的 init/tty/驱动依赖路径必须使用异步请求事件循环。异步信号另按[全局设计与冻结条件](00-overview.md)处理。
这不是并发处理保证，服务依赖仍需避免同步等待环及无完成保证的下游调用。

### recv 调用契约（已确定）

recv(options, event_mask) 一次交付 CALL、SEND 或合并 EVENT；种类/来源由内核填写，CALL 附接收方 REQUEST Handle，SEND 不建立可回复请求。
默认接收普通消息及 event_mask 匹配事件；RECV_EVENTS_ONLY 仅事件，RECV_NONBLOCK 无可交付内容返回 WOULD_BLOCK。event_mask=0 表示不接收事件，与 EVENTS_ONLY 同用拒绝；运行库默认封装显式提供事件掩码。
EVENT 只消费本次匹配位，未匹配 pending 保留；事件/消息均可交付时交替选择，普通消息 FIFO。失败不消费消息/事件或发布半份结果。
持有即时 CALL 尚未 reply/成功 defer 时再次 recv 返回 BUSY，不覆盖原请求；长期名额耗尽仍保留即时接收并回复拒绝的能力。
可交付检查、等待登记和阻塞切换原子协调，不能用非阻塞检查后单独睡眠替代。具体寄存器返回及 TIMER 代次字段遵守 ABI/事件规则。

#### 示例：筛选事件与保留 CALL

pending 为 TIMER|RX_READY，recv(EVENTS_ONLY, RX_READY) 只返回并消费 RX_READY，TIMER 保留。服务收到即时 CALL A 后，须 reply(A) 或成功 defer(A) 才能再 recv；错误调用返回 BUSY 而不丢 A。

### 接收公平与服务推进的边界（语义收口）

普通recv只需一个交替选择位，初始优先事件：合法FIFO队首消息与匹配pending事件同时可交付时，按该位选择并将下一次偏向另一类；只有一类时直接返回，不等待凑成两类。显式EVENTS_ONLY或事件筛选只对用户选择的方案集合工作，不承诺被排除消息/事件的公平，也不通过调用这些模式重置普通接收的交替位。

因此在持续调用普通recv且两类一直可交付的前提下，同一类之间最多插入一份另一类结果；这只约束内核选择次数，不承诺真实时间响应。服务若持即时CALL不reply/defer、同步等待下游或长时间不调用recv，内核交替选择无法替它处理取消/IRQ。服务线程被调度也不等于其业务主循环已处理事件。

EVENT一次取走本次掩码匹配的整个位集合，TIMER位与到期代次在同一提交点快照；未匹配位保持，新发生的置位不被旧快照清除。多个取消/完成/生命周期终结共用提示位时，实际有界记录表是权威来源，不按通知次数推进状态。

服务主循环接收提示后按类别分批推进：取消/终结清理、完成结果、IRQ设备队列及普通业务都有明确批次上限和继续游标，不能“把一类全部排空”后才处理其他类。一次提示可能覆盖超过单批预算的记录，剩余本地可推进工作必须保持本地待办标记；只要还有这种工作就继续轮转/有界让出，不重新阻塞等第二次提示。只有外部事件才能推进的请求不算本地可运行工作，不能据此忙轮询。

主循环可以先非阻塞recv、处理一批工作，确认本地无可推进项后再调用阻塞recv；后者仍须原子重查所有匹配内核状态并登记等待，所以两次调用间到达的消息不会丢失。不能把第二步换成不重新检查事件的裸sleep。各服务批次/超时和调度预算分别在自身实现验收，不把一个全局数字当所有设备最优值。

#### 示例：大量READ与一批取消同时到达

TTY已有长期READ达到上限，仍用保留即时名额接收一个新请求并回复繁忙；取消事件与新消息持续同时可交付时，普通recv交替选择。TTY一批只清理部分取消项，保留本地游标并继续轮转，即使所有取消只产生一次提示也能最终处理，不需要新增IRQ/取消消息队列。实际公平仍以TTY遵守有界主循环为前提。

### reply 调用契约（已确定）

reply(request, message) 校验当前服务持有的 REQUEST 类别/完整代次及已接收未完成状态，消息四字先复制成内核快照；SEND/EVENT 无可回复请求。
reply 是服务结束本地及下游对请求共享槽访问的承诺，不能成功后继续后台访问该槽；正常回复发布后客户端可使用结果和复用按协议已归还的槽。
协作取消标记不使原请求终结；服务仍通过原reply交付实际结果并收尾。只有调用者退出/exec等机制路径已强制终结时，合法迟到reply才丢弃业务结果、保持原错误并完成服务收尾；不覆盖客户端新现场。
服务只确认强制终结后的收尾可使用rqfinish；仅有协作取消标记时必须reply实际结果，不能rqfinish丢掉结果。已完成/已收尾/旧代次请求再次 reply 失败，不影响新请求。服务失去持有权限的请求不得凭旧整数完成。
普通 reply 不接收下一条消息；reply_recv 回复失败不接收，回复成功后进入接收，即使随后被中断也不撤回先前回复。

#### 示例：READ 的完成与取消

fs 接受 READ 后异步等待 blk，待下游完成并按协议发布读取结果、结束相关槽访问后 reply。若仅信号中断等待，原READ仍在同一Rq，服务回复实际字节数或保证零效果的EINTR；若调用者已退出/exec使Rq强制终结，迟到reply才仅收尾。

### defer 调用契约（已确定）

defer(request) 仅接受当前服务持有的即时 CALL，成功不回复调用者、不创建新请求或 Handle，返回状态 0 并保留原 REQUEST 身份。
检查长期名额/预付容量后，原子转入长期持有、占用长期名额并释放即时名额；容量不足返回 BUSY，原请求仍由服务即时持有，失败不丢弃或自动回复。
defer 失败须按协议 reply 繁忙等结果后才能继续 recv，不能持即时名额同步等待下游或覆盖该名额。重复 defer 状态错误，不重复扣费。
已强制终结请求不再进入新长期等待，只能reply/rqfinish收尾；仅协作取消的ACCEPTED仍可defer以安全排空既有下游并reply实际结果，不能据此新启动可避免的业务。defer和标记检查原子排序，长期名额保持到实际reply/收尾。
长期名额与服务持有记录在服务真正结束访问后归还，不因客户端等待结束提前释放。

#### 示例：tty 的延迟读取

tty recv 得到 READ 而暂无输入，defer 成功后继续接收输出/事件；输入到达后完成读并 reply。长期表满则 defer 失败，tty 仍持即时请求，先回复业务繁忙结果再接收，不丢 request。

### call 调用契约（已确定）

call(target, message, options) 校验调用者本地 IPC 授权，message 为四个 64 位字；默认同步，CALL_ASYNC 使用同一请求状态机但提交后不阻塞等待回复。
同步成功返回已取得回复，正常结果消费由内核完成，不另留须ack的RPC；PEER等同步机制错误若仍有下游收尾责任，也返回原RPC，不以错误返回伪造已安全归还。捕获信号在已入队后先撤离等待时，request字段总返回同一RPC（QUEUED/ACCEPTED均如此），不取消、不代消费/释放；由libsys保存并继续使用rqpoll/rqwait/rqack。信号在入队前先提交则没有请求，request=0；结果先提交则仍按正常同步返回，不多留RPC。
异步提交成功状态为 0，request 字段返回调用者侧 RPC Handle，其余提交输出按 ABI 清零；成功只表示请求已建立并进入交付流程，不保证已被服务接收/执行。
提交前检查授权、目标状态、参数及预付名额，失败不排队/不发布 Handle。短消息提交时快照，热路径不分配页/临时映射；共享大数据另依通道快照与槽所有权协议。
异步结果显式查询/确认，确认消费不代替服务收尾；call 不内置超时，用户态逻辑定时器驱动 rqcancel。需要响应普通事件的服务使用异步模式，不能同步阻塞后期待 TIMER 强制打断。

#### 示例：init 异步读取程序

init call(fs, READ, CALL_ASYNC) 获得 RPC Handle，继续处理退出/设备/管理请求；完成事件到达后按该 Handle 查询原请求结果，不按事件次数推断完成数量，也不重新发 READ。

### 异步结果查询与确认（已确定）

rqpoll(rpc, options)、rqwait(rpc, options)、rqack(rpc, options) 只接受调用者自己的 RPC 类别完整身份，不能查询他人 REQUEST。rqpoll 未终结返回 WOULD_BLOCK，已终结返回保存的回复或终结错误；rqwait 未终结则原子登记等待，已终结立即返回。
查询/等待不消费结果，终结结果不可被迟到回复改写；libsys 保存结果后 rqack 确认消费，未终结 ack 返回状态错误。客户端确认不代替服务收尾。
普通完成事件可合并，真实结果保存在 Rq 中；rqwait 的结果检查与等待登记须原子协调。ack 后不得重复向应用交付结果，但仍须存在明确的服务收尾观察及最终句柄释放协议，不能立即丢弃旧槽身份；释放契约见下文。

#### 示例：先确认机制失败，后安全收尾

异步调用尚未完成时 rqpoll 返回 WOULD_BLOCK，正常完成后 rqwait 读取，libsys 保存再 ack。若接收服务失效等机制已强制终结，则可先确认失败结果，但仍在访问旧缓冲时保持收尾记录，不能提前复用共享槽。

### rqack 的确认与释放（已确定）

rqack(rpc, options) 支持 ACK_RESULT 确认结果消费及 ACK_RELEASE 放弃跟踪。未知位/零选项拒绝；确认要求请求已终结，释放要求结果已确认且 server_finished。组合调用整体检查，失败不部分修改。
ACK_RESULT 后不再交付业务回复，rqpoll 仍可查询收尾状态；最终跟踪释放前，记录和 RPC 身份持续有效。ACK_RELEASE 成功后旧 RPC 失效，槽按代次规则回收，不能再依其查询结果。
重复 ACK_RESULT 在同一未释放记录上幂等；重复最终释放使用旧 Handle 时返回陈旧错误，不影响新请求。同步正常返回由内核代为消费/释放，调用者退出也代为放弃，但服务未收尾不得释放相关资源。
结果确认与服务收尾为独立持久状态，结果已确认后发生服务收尾也须置完成提示，供库重新扫描；事件合并不丢状态。收尾期间使用 RQ_FINISH 查询/等待，不能以普通已终结结果的立即返回循环忙等。

#### 示例：机制强制终结后分两次确认

正常 reply 已承诺收尾，库保存结果后一次 rqack(ACK_RESULT|ACK_RELEASE) 完成。机制强制终结后服务/下游仍使用旧槽时，库先ACK_RESULT，保留 h 查询；确认 server_finished 后归还共享槽并 ACK_RELEASE。回收条件为 caller_consumed、server_finished、caller_released 全部满足。

### rqcancel 调用契约（第6项审查修订）

rqcancel(rpc)仅操作调用者自己的有效RPC，短提交、不等待服务。取消与recv/reply在同一状态转换保护下排序：

| 原阶段 | 动作及后续结果 |
| --- | --- |
| QUEUED | 原子摘队，形成CANCELLED机制终态、server_finished=true，归还未用接收资源槽；保证该Rq未交付、不会产生效果 |
| ACCEPTED | 只置cancel_requested并提示接收服务，仍为ACCEPTED、owned及预留接收槽保留；rqpoll可继续WOULD_BLOCK，服务必须reply实际业务结果 |
| TERMINAL | 返回成功但不改变既有结果；已回复成功不被取消撤回 |

重复设置幂等，旧代/其他主体RPC拒绝。返回0只表示取消请求已记录，不能解释为业务已撤销、结果已终结或DMA停止。cancel_requested只表达尽快停止尚未完成部分；服务若尚无效果，应停止后续执行并回复保证零效果的业务EINTR；已有部分/完整效果则回复实际数量、资源或真实错误，不能为了响应取消伪造零效果。内核不解析上述业务，也不把标记强制转为EINTR。

服务对其持有REQUEST调用rqcheck，a1为位值：LIVE=1、CANCEL_REQUESTED=2、DRAINING=4。正常ACCEPTED返回1，已请求协作取消的ACCEPTED返回3；机制已强制终结而未收尾返回4。3仍允许普通/资源reply，4仅允许丢结果收尾或rqfinish。已完成、旧代、跨接收者请求拒绝，不把当前PID的其他请求当持有关系。

取消提示可合并，服务每批有界检查owned记录，优先推进取消与完成，不需要新的CALL或共享控制槽。尚在设备/下游执行的操作必须取得实际结果或安全停止，不能收到标记即归还槽。

调用者退出/exec及接收者退出/exec仍可由机制强制终结；这是与协作取消不同的路径，已接收的共享/DMA责任转DRAINING并保留，迟到reply不改强制错误。普通逻辑超时不是原生终结事件：POSIX协作取消后的1秒故障等待按11推进，库可rqcancel并把原RPC/缓冲/已安装资源责任转入预付后台记录，报告明确超时/EIO；结果不明不得重试业务，也不得以返回用户为由提前ACK_RELEASE或复用槽。若服务永不响应，保持有界背压并进入监督/隔离，不假造server_finished。

#### 示例：取消与部分写竞争

WRITE已被FS接收，信号先退出等待并返回h；rqcancel(h)置标记，FS已接受128字节则在原reply返回128，调用者只消费这一次结果。若取消先于recv摘队，则h得到CANCELLED并保证无效果。若FS已经回复，rqcancel不改变原结果；三种次序都无需另发RESULT查询或重做WRITE。

### 请求结果与收尾等待（已确定）

rqpoll/rqwait 的默认模式查询/等待终结结果，RQ_FINISH 模式查询/等待 server_finished；未知选项拒绝。poll 条件未满足返回 WOULD_BLOCK，wait 原子登记等待并阻塞。
RQ_FINISH 成功返回状态 0，不交付业务回复，不确认结果、不自动释放跟踪；ACK_RESULT 后默认领取结果返回状态错误，但仍允许 RQ_FINISH。ACK_RELEASE 后旧 Handle 失效。
等待服务收尾被信号打断仅结束本次等待，不释放 RPC、不取消原有收尾义务；再次等待使用同一身份。等待原请求结果时被信号打断的完整取消策略由调用包装按其契约执行，不能把查询等待中断偷偷等同原请求取消。
结果终结和服务收尾均可置完成提示，接收者扫描持久状态；服务收尾先发生则后续 wait 立即成功，不要求提示仍 pending。响应型服务使用事件循环和 poll，不因等待一个收尾阻塞全部控制。

#### 示例：机制失败后的阻塞收尾等待

机制失败结果取得并ACK_RESULT后，rqwait(h,RQ_FINISH)等服务rqfinish或可信代收尾；返回 0 后库归还共享槽并 ACK_RELEASE。信号中断等待时继续保留 h 和槽，下次查询不会因旧结果已终结而误判收尾完成。

### 原生 IPC 的捕获信号中断矩阵（第6项审查修订）

用户已接受：原生 IPC 一律不根据 SA_RESTART 自动重启；以下 INTERRUPTED 是原生状态语义，不提前分配错误数字，也不由 libsys 反向操作 libc errno。POSIX read/write、进程操作等适配层仍按自身已选规则决定继续/返回；通用 ipc_* 包装不猜服务业务、不重发消息。

| 原生操作及阶段 | 捕获信号先取得中断结局时 | 已固定结果先于信号时 |
| --- | --- | --- |
| 同步call，尚未入队 | 无请求，返回INTERRUPTED且request=0 | 提交先成功则依下列阶段处理，不能丢请求 |
| 同步 call，QUEUED | 仅退出等待，INTERRUPTED及原RPC；不摘队、不取消、不消费 | 保留原终态，不重发 |
| 同步 call，ACCEPTED 且未终结 | 仅退出等待，INTERRUPTED及原RPC；原请求继续，可显式rqcancel提出协作取消 | 保留已固定回复/错误/资源交付结果，不取消已提交成功 |
| call(CALL_ASYNC) 的短提交 | 不设置可中断等待；信号在提交前或提交后递送，不能产生已入队却丢失 RPC 的半成功 | 保留提交成功及同一 RPC，不自动等待或重发 |
| send，仍排队 | 原子摘队并返回 INTERRUPTED，request=0，无服务排空责任 | 消息完整复制即成功，保留成功，无 RPC/REQUEST |
| rqwait，默认结果等待 | 仅撤离当前等待并返回 INTERRUPTED；不 rqcancel、不 ack、不释放原 RPC | 保存本次查询快照，不消费，不在 handler 后再查来覆盖它 |
| rqwait，RQ_FINISH | 仅撤离当前等待并返回 INTERRUPTED；原收尾责任/槽继续保留 | 保存 server_finished 已满足的成功，不自动 ACK_RELEASE |
| recv，无消息/事件已提交 | 撤离等待并返回 INTERRUPTED，不取走任何消息/事件 | 保留已接收的 CALL/SEND/EVENT 及完整来源/请求/事件快照，不再次 recv |

同步call中断返回的RPC是原结果的唯一领取身份，不只是清理Handle；在Sigctx/原Rctx中稳定归属后才允许handler重入。reply在中断结局之后提交时写回原Rq，不写当前用户寄存器；handler返回后查询同一RPC。中断与回复若都已发生，以已原子确定的等待返回为准：中断先提交则仍返回RPC并显式查询/确认，回复先提交则走原同步成功路径。不得因服务很快完成就丢失中断路径的RPC或代为消费结果。

rqwait 的“等待被中断”与“读到原 Rq 的中断/取消终态”是不同语义，即使最终编码可能共用部分状态值。调用者始终保留输入 RPC，可用 rqpoll 查询原请求的持久终态；是否主动 rqcancel 由上层协议决定。查询/等待本身不消费，不能通过默认 rqwait 已立即返回终态推断 server_finished。原生等待INTERRUPTED与原请求QUEUED/CANCELLED分别按06编码；不增加平行业务结果输出。

recv 的接收提交包含请求 owned/即时名额归属或匹配事件位的取走，以及完整结果保存；必须与信号中断原子排序。CALL 已提交但外层尚未处理时，handler 再普通 recv 仍受唯一即时名额的 BUSY 规则约束，不覆盖旧 REQUEST。EVENT 已取走的位保存在外层结果，新到同位事件仍按 pending 机制保留；不能把外层快照重新塞回 pending 冒充未接收。

reply_recv 分两段：reply 失败则不接收；reply 成功后 recv 被中断，只返回接收段的中断，不回滚回复，也不能自动重做 reply_recv。短提交类的 reply、rqcancel、rqack、rqpoll 及非阻塞 recv 不设置可中断睡眠点，其已提交副作用/查询结果在信号后保留；真实校验/状态错误照常报告，不通过信号制造“可能 ack 了但应重做”的结果。

纯 STOP 保留真实等待、结果和等待边，不隐式取消；CONT 后核对持久状态。若 CONT 另需捕获 handler，则走相应的捕获信号中断路径。KILL 不返回用户，等待边撤离及 caller_consumed/caller_released 按既有死亡清理推进，不伪造 server_finished；仍访问中的共享/DMA 缓冲继续隔离计费。

例子一：A 异步提交 READ 得到 h，随后 rqwait(h) 被信号打断，handler 返回后是 INTERRUPTED；READ 仍可正常完成。A 可再次查询/等待 h，或显式取消；不能因等待中断便回收共享槽。同步call READ的捕获信号采用同样的退出等待语义，并在request返回原h；两者都只从原Rq取结果，不需要另建业务查询请求。

例子二：服务 B 的 reply_recv 已成功回复 A，接收下一条前被信号中断。handler 返回后 B 只处理接收中断，可另行 recv；重做原 reply_recv 会再次使用已失效 REQUEST，不能作为重启实现。若接收下一条 CALL 已先提交，则保留该 REQUEST，handler 的 recv 不能抢占其即时名额。

原生错误见06，稳定信号/库记录与外层RPC归属见本篇及08/11首版规格；尚未实现，不宣称本矩阵运行通过。

### rqfinish 调用契约（已确定）

rqfinish(request)仅接受当前服务持有、机制强制终结且未收尾（rqcheck=4）的REQUEST；仅cancel_requested（rqcheck=3）仍须reply实际结果，不能用finish丢结果。重复/陈旧/跨主体finish拒绝。
调用前结束本地及下游对请求共享槽的访问，或将剩余工作转移到与旧槽无关的独立缓冲；DMA 不得继续访问待归还区域。取消通知本身不是这些条件的证明。
成功标记 server_finished，归还服务持有名额并提示调用者查询，不交付业务回复或改写既定取消结果；内核只检查可验证的请求归属/状态，服务承担协议收尾承诺，不能宣称内核验证了任意设备是否停止。
服务死亡由内核/可信管理清理接管，内核阻止服务继续运行并撤销访问路径，init 协调下游/设备收尾；未证明所有必要访问者结束时，区域保持隔离，不以服务死亡直接宣称共享槽安全。
代收尾使用下述受限管理入口，不能放宽普通 rqfinish 的主体校验，也不能因退出卡住就提前发布 server_finished。

#### 示例：取消 READ 的下游收尾

客户端退出/exec强制终结READ后，fs取消/排空blk下游操作，待blk不再访问关联缓冲后释放本地引用并rqfinish；客户端仅rqcancel时仍reply实际结果。若 fs 在此期间退出，则其代次所属请求/区域转交管理清理，blk 仍可能在工作，不能立即归还客户端槽。

### rqclean 管理代收尾（已确定）

rqclean(owner, request) 仅由持有专门清理授权的 init 使用；owner 在调用者表解析为原接收服务实例的管理授权，request 按其原接收者身份及完整代次定位，不能冒用调用者的普通 REQUEST 权限。
仅在原接收镜像已停止执行、请求已移交退出/镜像替换清理、必要下游/设备访问结束时确认收尾。内核验证原实例及镜像代次、归属、清理阶段与权限，可信 init 按服务协议确认不可由内核直接观测的下游排空条件。同PID新镜像仍运行不等于旧镜像仍拥有该请求。
成功发布 server_finished 并释放对应服务持有引用，不改变客户端已确定失败结果，不代表 init 执行业务或重放操作；陈旧/其他归属/仍运行服务请求拒绝。重复完成原身份返回终态/陈旧错误，不影响复用请求。
管理授权及孤立请求枚举在退出清理完成前保留，独立于可复用进程槽；枚举具体分页/结果布局在管理查询 ABI 冻结。无法证明 DMA 安全则保留/隔离，不调用成功确认来伪造收尾。

#### 示例：fs 死亡但 blk 仍工作

fs 持 READ 等待 blk 时崩溃，内核冻结原归属并向客户端发布失败；init 查询旧 fs 尚未收尾请求，协调 blk 排空旧连接/区域后 rqclean(owner, request)。客户端再观察 RQ_FINISH，按协议归还槽并释放跟踪。
若旧 fs 进程槽已复用，管理授权仍定位原实例清理记录；旧请求不能经新 fs 的管理授权完成，也不能因槽号相同清理新实例资源。

### Rq的最小内容与持有关系（布局讨论稿）

在既有固定请求池内统一维护请求，不新增公开事务对象。下面是逻辑字段分组，不是C结构声明或已验证字节数；最终只保留实际需要的信息，布局按两架构共享不变量与内存报告冻结。

| 内容 | 最小责任 |
| --- | --- |
| 身份 | 请求槽代次、调用者与接收者完整实例/镜像；服务REQUEST和调用者RPC是同一记录的不同授权视角 |
| 来源 | 提交时的本地授权完整身份及已校验范围，具体对象的稳定引用；不把可复用表项裸指针当唯一来源 |
| 消息/结果 | 排队请求四字，或提交后的四字回复/资源标记、机制终结结果；结果一旦终结不被迟到取消改写 |
| 队列与服务持有 | 独立queue/owned侵入式节点、即时/长期配额归属；一个节点不能同时挂不同用途队列 |
| 收尾 | caller_consumed、server_finished、caller_released及必要取消状态，三项责任分别成立后才回收 |
| 等待关联 | 同步等待所属上下文身份/代次或异步结果归属，不能保存退出后悬空的用户指针或内核栈续点 |
| 可选交付 | 本次接收种类及一个预留资源槽位置/有效标志；普通请求不额外分配交付对象 |

本地授权来源可用调用者实例/镜像加完整本地Handle标识，提交时已取得的对象引用与权限快照保证后续操作安全；revoke按精确来源匹配，free不导致旧请求读取同槽新授权。具体字段去重与是否共享已有稳定引用在布局审查时决定，不机械给每个身份再造一层对象。

请求与回复消息方案复用同一个32字节存储：入队时保存输入，接收时先完整复制到服务的用户返回现场，再结束该输入的内核持有；终结时覆盖为结果。内核不提供重放原请求，也不保存服务业务快照，因此不必同时持有两份Msg。失败/取消的机制结果同样不得使未读到的原输入被当成功请求交付。若某项确定需求需要原输入长期保留，必须单独证明，不能用未实现的假设强行套联合存储。

同步阻塞的C续点属于线程栈，不塞进Rq。Rq只在实例/镜像/等待上下文仍匹配时交付保存的结果；handler、exec、退出或槽复用后不能通过旧指针恢复新调用。服务结果可保存在Rq等待调用者查询，不能为释放线程栈顺便销毁仍需排空的Rq。

资源预留也只归该Rq：QUEUED取消、机制强制终结或普通回复时解除未用槽；ACCEPTED协作取消保持预留；资源回复在同一提交点把预留转为调用者本地授权，之后Rq不再拥有这份资源引用。结果仅保存接收方Handle数值和资源标记，重复查询不再执行引用转移；调用者是否已free该引用不导致Rq“重新补发”。

客户端已消费但服务未结束时保留收尾记录，不必为此保留完整线程现场、业务文件或用户地址空间。Rq也不直接持有File/TTY会话或解析DMA描述符；服务独立记录实际访问者，内核请求完成与共享页可复用继续分开。

#### 示例：取消READ后线程栈已退出

A的READ被信号中断，内核调用链退出并进入handler；原Rq仍可能排队/执行。FS后续reply把实际结果固定在原Rq，不能写handler的新寄存器或新请求槽；只有机制强制终结后才丢业务结果而仅收尾。三项回收条件成立才推进Rq代次，不依赖A的旧内核栈还存在。

### Rq转换与线性化点（已冻结）

阶段仅描述请求是否交付/终结；终结结果、服务收尾和调用者确认分开。一次终结提交固定机制结果及普通/资源回复，后续只推进剩余责任，不重新选择终结原因。

| 动作 | 原阶段 | 原子提交及持有关系 |
| --- | --- | --- |
| recv接收 | QUEUED | 摘queue、挂owned、复制完整请求到接收现场，转ACCEPTED；调用者结果尚未终结 |
| 普通/资源reply | ACCEPTED | 固定结果，转TERMINAL，server_finished=true，摘owned；资源安装与结果一起提交 |
| rqcancel | QUEUED | 摘queue，转TERMINAL/CANCELLED，server_finished=true，释放未用接收槽；保证未交付 |
| rqcancel | ACCEPTED | 仅置cancel_requested并提示，仍ACCEPTED/owned，server_finished=false，保留资源接收槽 |
| 捕获信号退出call/rqwait | QUEUED或ACCEPTED | 只移除当前等待边，原Rq/槽/结果领取责任保留，不转TERMINAL |
| 对取消请求reply/rqfinish | TERMINAL且未收尾 | 校验原接收者/镜像，server_finished=true并摘owned；不改原结果、不安装资源 |
| 接收服务退出/exec | QUEUED或ACCEPTED | 排队请求按未交付终结且无服务收尾；已接收请求按可能已执行终结，收尾引用转旧Life，不能直接置server_finished |
| rqclean | 接收者已终结且TERMINAL未收尾 | 管理者确认实际下游安全后结束收尾、摘旧持有关系，不改失败结果 |
| ACK_RESULT | TERMINAL | 置caller_consumed，只消费结果，不代替服务收尾 |
| ACK_RELEASE | TERMINAL且已消费/已收尾 | 置caller_released，不改变资源交付所有权 |
| 调用者退出/exec | 任意在用阶段 | 若未终结强制转TERMINAL；未接收则摘队/已收尾，已接收保持owned和DRAINING；释放未用资源接收槽并代为放弃结果/跟踪 |

调用者不存在时可由内核同时置caller_consumed/caller_released，即使服务尚未收尾；这是死亡代收取，不允许存活调用者用ACK_RELEASE跳过收尾。同步正常返回由内核代消费/释放；同步中断后交付原结果RPC，由运行库继续领取/确认；只有强制终结未收尾才按DRAINING处理。任何路径都不能只为释放槽而伪造server_finished。

查询是快照且不推进消费；重复rqcancel不改已终结结果，重复ACK_RESULT对仍存在同代记录幂等。reply/rqfinish在服务收尾后旧REQUEST失效，不能当作再次完成；最终释放/池复用后的旧RPC必须失败，不把它解释为新请求的重复动作。

服务死亡后owned由旧Life/清理归属继续持有，不再要求旧Proc或内核栈存活。若硬件始终不能确认安全，状态可以持续TERMINAL未收尾并占配额，这是明确隔离状态而非证明最终一定回收。调度公平和事件通知不能替代物理访问安全证据。

#### 示例：强制终结先于资源回复

请求已ACCEPTED并预留接收槽，调用者退出/exec先提交使其TERMINAL/未收尾并归还槽。服务随后合法reply只能收尾，不得向已复用的槽安装资源。仅rqcancel置协作标记不归还该槽，合法资源reply仍可安装实际结果。反过来资源reply先提交，则结果和安装已成功，rqcancel只观察既有终态；异步查询和确认都不再执行安装动作。

### CALL 绑定的单资源回复交付（已冻结）

方案以已有CALL/Rq承载一次受限交付，不给服务客户端管理权，也不创建独立offer对象。只在建立/更新共享连接的明确请求中使用；普通读写继续走短消息/共享槽热路径。选项/位值、参数位置及56字节描述符以06为准，尚无运行实现。

1. 调用者在call选项明确同意接收一个指定允许种类的资源；内核在请求入队前为其预留一个本地资源槽，绑定完整实例/镜像及本次Rq。槽不足则请求不交付；普通call不预留也不能被强制安装。
2. 服务准备好资源后，用reply的资源交付选项和固定描述符回复。描述符含服务本地source Handle、减小的操作范围、内存窗口及三个业务回复字；内核一次复制并验证，不跟随嵌套指针。
3. 内核校验source授予权、接收种类、请求归属、原调用者镜像及预留槽，取得引用后在短提交段原子安装新Handle并提交回复。失败撤销本次引用，不暴露半安装。
4. 回复仍为四字Msg：words[0]由内核填入调用者本地新Handle，words[1..3]为业务回复。只有此显式格式占一个消息字；普通reply的四字含义不变，内核不解析FS业务错误。

允许种类收窄为普通SharedMem的受限映射权，以及明确可授予的后端CALL权。禁止私有进程内存、可执行权、DMA/MMIO、IRQ、构造/监督/预算管理权；接收者不自动获得转授权。Mem仍由原Acct出资，接收者自己的映射/页表另按既有规则计费，交付不迁移物理页费用。

接收同意来自内核保存的本次call选项，不信任业务消息的PID或布尔值。只能安装到请求原调用者，服务不能另指定接收PID或覆盖已有资源；同意仅覆盖一个预留槽及允许种类。

#### 回复、取消与失败

- 调用者退出/exec或对端失效等机制强制终结先提交：不安装资源，释放未用预留槽；迟到合法reply仅按既有规则服务收尾，不改写取消结果。非法描述符仍按参数错误处理，不伪造完成。
- 资源回复先提交：Handle与回复已交付，晚到取消不撤回。异步结果按原Rq查询/确认，资源引用独立归调用者，不随rqack释放；包装层放弃结果时须按清理协议释放资源，不能只丢数字。
- 服务业务失败：普通reply返回业务错误并归还未用接收槽。内核不解释业务成功字段，由服务明确选择是否交付资源。
- 描述符/授予权检查失败：回复未提交，请求仍需合法reply/rqfinish；预留跟随原Rq，不被其他请求占用。

成功安装后该槽成为普通授权；未交付、失败或取消才归还预留。源服务自己的引用保持独立，失败不能误释放source，成功也不授予服务任意撤销对方映射的权力。服务按连接限制共享区总量，接收者仍持引用时不能擅自复用物理页；额度耗尽拒绝新连接。

首轮只给独立reply定义这条冷路径，不增加send转移、请求侧任意附带对象或reply_recv混合交付。共享区与后端CALL权可分两次握手并缓存，不使每次数据I/O重新交付。连接协议仍须补齐部分成功补偿、引用释放和后端来源校验，不能把单次交付当完整open成功。

#### 示例：客户端取得FS共享缓冲

A已有FS的CALL权，以同意接收SharedMem的请求申请通道。FS按A的连接配额分配共享Mem，以受限窗口回复；内核将新Handle安装到A并放在words[0]，A再显式map。A先取消则不留授权，FS保留原Mem并清理失败准备；回复先成功则A使用自己本地的Handle，不是FS的source整数。

### 单资源回复的标记与参数（ABI草案）

接收端必须凭内核结果元数据辨认交付，不以words[0]看起来像Handle或业务状态为依据。方案使用已有kind结果位置：普通同步回复为0，成功资源回复为RESOURCE_REPLY；source/request保持普通同步回复的0。kind只有在本次引用已安装并提交回复时由内核设置，不能由普通服务消息伪造。

CALL的接收同意方案分为接收SharedMem、接收后端CALL两种互斥选项，可与CALL_ASYNC组合；同时选择两种或未知选项拒绝，不隐式同意任意种类。异步提交只返回RPC Handle，完成结果在rqpoll/rqwait中保存同一RESOURCE_REPLY标记与四字回复；重复查询不重新安装，ACK_RESULT之后的收尾查询不再交付已消费资源结果。

reply的资源选项采用以下参数位置，不增加调用号：a0/x0为REQUEST，a1/x1为固定描述符的用户地址，a5/x5为资源回复选项，其余参数为0。普通reply的a1–a4/x1–x4仍是四个消息字；只有明确选项才按描述符地址解析，不能猜指针。reply_recv/send使用资源选项拒绝，不部分执行。

固定描述符方案为七个连续8字节字段，合计56字节：source为有符号Handle，rights/offset/length以及三个业务回复字为u64；按8字节对齐，最终C定义/偏移断言随共享头冻结。没有接收PID、目标槽、嵌套指针、可变资源数组或兼容版本链。内核一次复制后校验，不在等待期间重读描述符。

CALL授权不是范围资源，offset/length必须为0；SharedMem窗口必须在源授权内且满足映射窗口规则，不因伙伴块取整扩大。服务必须实际持有可授予的source，不能凭后端PID或收到客户端请求就生成授权。服务回复侧仍只返回机制状态，资源Handle仅返回给原调用者，不把目标本地整数当source服务自身新权限。

只有RESOURCE_REPLY标记证明新Handle来自本次安装。普通reply即便words[0]恰好与某个有效Handle相等，也只是业务数据，运行库不能据此自动map/free。标记资源种类仍须与本次调用同意及连接协议一致；业务结果为错误时包装层按记录清理已交付引用，内核不解析业务错误来回滚授权。

#### 示例：普通错误码不被当资源释放

A同意接收SharedMem，但FS普通reply报告业务失败，words[0]碰巧是正整数。内核归还未用槽并返回kind=0，包装只按业务格式处理，不能把该整数当Handle去free。FS使用资源reply且提交成功时，kind=RESOURCE_REPLY，words[0]才是已安装的本地授权。

### 交付结果的持有与连接失败补偿（已冻结）

跨VFS/TTY的两次交付及未接入会话清理见 [直达后端首次连接](10-filesystem.md#直达后端的首次连接已冻结)。接收同意只解决内核资源安装，不替代VFS授权、后端会话校验和第三方准备的生命周期责任。

一次成功资源reply只安装一份引用。异步rqpoll/rqwait重复读取同一结果返回相同已安装Handle，不重新安装、不递增资源引用；rqack只消费/释放Rq跟踪，不替调用者free资源。内核收到已终结请求的重复资源reply不得再次安装。相同业务操作号的跨新Rq重试也不能无条件重新交付：优先查询保留的原Rq结果，业务重试/重新连接必须确定旧状态，不把缓存source整数当接收方已安装Handle。

运行库在ACK_RESULT前将收到Handle转交连接对象或预付清理记录，之后才放弃结果查询权。同步正常返回仍须在信号安全进行中记录中保持结果；若包装随后失败，已安装资源由包装负责释放，不能把“包装失败”当“内核没有安装”。资源放弃复用 [本地free](03-process.md#本地资源引用的放弃已冻结)，它不代替服务会话关闭。

| 失败点 | 客户端责任 | 服务责任 |
| --- | --- | --- |
| 资源回复之前取消/业务失败 | 取消原Rq并等必要收尾，无本次新资源可释放 | 释放本次未发布会话/源Mem；仍在使用的缓冲按原协议保留 |
| 已收到Mem，map失败 | 保存原结果，按同一连接操作取消准备，free未映射引用 | 按原实例/操作序号释放本次会话与自身引用 |
| 已map，后端CALL交付失败 | 禁止连接发布，排空相关请求后unmap/free已取得引用 | 撤销本次已准备的后端会话，不动其他连接 |
| 资源已交付但调用者死亡 | 内核按该实例清理本地表/映射，遗留请求继续独立收尾 | 根据终结观察清理会话，不依赖死者发送abort |
| 服务死亡或回复状态不明 | 查询原Rq，不自动重做；保留不能证明安全的共享区 | 服务恢复按旧实例隔离，不能把新服务上线当旧访问已结束 |

服务以可信调用者、服务实例和连接操作序号保存有界准备/取消结果，补偿幂等；确认过的旧操作不能再次激活新会话。控制/取消路径的Rq和本地记录必须预付，不能因待清理连接占满数据槽就无路取消。

#### 示例：共享区已取得，后端连接失败

A已拿到并map共享Mem，后续取得后端CALL权失败。A不把半连接写入可用fd表：先按原操作请求收尾，相关访问完成后unmap并free本地Mem；服务关闭原准备并放弃自己的引用。若服务失联而下游仍可能访问，继续保留缓冲并计费，不为了恢复额度提前复用。再次连接使用明确的新实例/操作身份，不接续旧不确定请求。

## 数据与共享内存

短控制消息通过寄存器，路径和大块数据走预建立共享内存。
RPC 热路径不申请堆或物理页、不临时映射、不传权限；复用预付 Rq，其内嵌队列节点支持 FIFO 常数时间入队/出队。
共享数据仍需边界检查及必要快照，不能信任其他进程不会并发修改。
块驱动先保留私有 DMA 缓冲，不要求端到端零拷贝。

### 共享通道（已确定）

每个客户端与服务使用独立、有上限的共享缓冲，不让所有客户端共用可写区。
引导期init可按管理授权建立共享区；普通连接由双方按受限授权协作，不逐次请求init。普通grant的目标配置权不用于任意运行中客户端；已选单资源reply补齐[受限资源交付](03-process.md#grantrevoke-的目标边界审查收口)，实施时必须保持双方同意/容量/协作取消及强制终结规则，不用更换协调者名称冒充协议已完整。
消息只传操作、偏移、长度等，不传对端虚拟指针；服务按内核提供的调用者完整身份选择连接并检查范围。
每个共享缓冲槽最多一个使用中的请求；每执行上下文、异步请求使用各自槽，禁止复用仍由服务或下游使用的槽。
文件/TTY的具体布局见10第7项修订：同一客户端镜像/后端镜像一条连接，控制页集中128字节描述符，4 KiB数据页按上下文分区，冷路径最多占两页，不为handler复制整条连接。span在用户态私有表中绑定原Rq，不扩宽32字节内核Msg。
面对不可信客户端仍须快照控制信息及必要写入数据；内核页固定不能替代协议快照。
成功回复后按协议复用；尚未接收的请求取消完成后可复用，已接收请求的取消不代表服务/下游已停止访问。
重建连接优先新建共享区，旧区按引用和设备收尾条件释放，不以修改代次替代安全回收。
通道是用户态连接配置与共享区的组合，不新增内核通道对象。
共享槽与独立请求记录的收尾协议见[全局设计与冻结条件](00-overview.md)；文件共享布局/大小以10为准，设备协议常量以09为准，内部实现仍待验证。

## 必须先解决的阻塞模型问题

已选择有上限的延迟回复：tty 暂存读取请求并继续处理输出，init 暂存退出等待请求并继续处理管理请求。
新增独立 reply(request_id, response)，reply_recv 保留合并回复和接收的快捷路径。
请求记录来自进程创建时预付的全局有界请求槽，不按请求分配堆内存；支持异步请求和信号中断后的独立收尾。
服务用户态暂存表有固定上限，不能无限接收并遗失标识；内核接收容量不得超过该表可承载的数量。
请求标识使用统一 64 位 Handle，低位索引请求表而非进程表；槽代次区分每次使用，耗尽不回绕。
回复检查请求仍有效、调用次数匹配、接收服务身份匹配且未回复；成功后标识失效，不可转交或复制为授权。
服务长期暂存容量与即时分发名额分开：defer 成功才持有长期请求，满额时仍接收并回复/拒绝新请求，不遗失请求标识。
reply_recv 回复成功才继续接收；回复失败立即返回错误、不隐式接收新消息，服务可另行 recv。

调用者退出时，内核先使请求失效，再向接收服务设置可合并的 CANCEL 事件，并按接收状态唤醒服务。

事件由 recv 原子取走，rqcheck 不清除事件；查询期间的新取消继续留下事件，避免丢失清理通知。
有效性查询只是快照，reply 必须重新验证。已释放请求记录的旧标识只返回无效，不因槽位复用恢复有效。
无需为每次取消分配独立事件记录；服务暂存表有上限，批量查询可分批完成。
机制已强制终结后不得再启动依赖旧缓冲的新业务；仅协作取消仍须保留原输入/结果及收尾归属；异步硬件操作的收尾及 DMA 生命周期另行处理。
保留单线程服务，不通过增加线程或为每个操作拆服务规避等待问题。
sh 执行外部命令后应释放输入读取，避免与子进程争抢输入。

- [ ] 用“等待终端输入时另一个进程输出”和“等待子进程时处理其他请求”检验 IPC/事件方案。
- [ ] 定义请求、事件的公平性和背压，不使用忙轮询代替阻塞。

### 请求状态、取消与缓冲归还

Rq方案只保存QUEUED、ACCEPTED、TERMINAL三个在用阶段，空闲由请求池管理，不再独立保存REPLIED/DRAINING/RETIRED枚举。DRAINING是TERMINAL且server_finished为假的派生状态，回复成功是终结结果种类，允许回收由三项责任共同决定，避免状态枚举与完成位互相矛盾。
QUEUED的rqcancel形成CANCELLED且server_finished=true；ACCEPTED的rqcancel只置cancel_requested并保持原阶段/owned，只有机制强制终结才派生DRAINING。回收仍必须同时满足caller_consumed、server_finished、caller_released及无队列/观察临时引用，不能只检查TERMINAL。
提交时绑定调用者侧槽与完整实例身份；服务端 REQUEST Handle 与调用者侧 RPC Handle 类别不同，分别校验主体，不可转让。
正常reply形成终结结果并承诺不再访问该请求共享槽/下游引用；回收还要求调用者结果消费并释放跟踪（或退出代为放弃），之后才能复用请求槽。机制强制终结本身不包含服务收尾承诺；协作取消更不代表结果已终结。

- 运行库每连接提供配置数量的共享槽，每槽有请求身份和使用期；旧槽仍执行、未保存或DRAINING时新操作只能用自己分区内其他空页；无空页按10的EAGAIN/关闭EIO规则处理，不窃取信号保底。
- 内核不解析文件/通道协议、不引入通道对象；用户协议将共享槽与 Rq 的收尾结果绑定。固定页只防物理释放，数据安全仍由快照及槽隔离保证。
- 服务在 reply/rqfinish 前必须结束本地和下游对该槽的访问。下游还在 DMA 时先保留私有 DMA 缓冲和关联记录，不能提前确认收尾。
- 调用者退出后 Rq/关联账目可脱离进程槽保留；服务退出使客户端获得失败，但下游引用由其实际持有者独立收尾，旧区不得直接复用。
- 共享数据只作运行库 staging，不让服务在客户端 EINTR 返回后继续写应用原始私有指针；读结果只在匹配请求成功后复制回应用。
- 捕获信号只结束当前等待，rqcancel只提出取消请求；两者都不保证已接收业务停止。运行库区分等待、原结果和槽归还，未安全归还的槽由后台记录或退出清理继续持有。

请求的三个完成点分别是等待结束、服务收尾和记录回收：等待结束不能推导共享槽可复用，服务收尾不能推导客户端已消费结果。
记录复用必须同时满足客户端已消费/放弃结果、服务已确认收尾和调用者已释放跟踪；之后才递增请求槽代次。
同步正常 reply 是服务收尾承诺，不能成功回复后继续访问该请求共享槽。
同步 INTERRUPTED 的非零 RPC 收尾 Handle 由运行库持有并跟踪，不能丢弃后直接复用旧缓冲。

验收：取消后立即新请求、服务延迟读写、调用者/服务交叉退出、下游延迟完成；旧槽隔离，配额有界，最后引用精确归还。

### 容量、分发与控制进展

- CONFIG_PENDING_CALLS 分为一个即时分发名额和其余长期 defer 名额；需要长期等待的服务配置至少两个名额。取消已占用的长期记录直到 rqfinish 才归还，避免旧请求仍占服务表而内核超额分发。
- recv 取 FIFO 队头 CALL 到即时名额；服务可立即回复，或通过 defer 原子转入长期配额。defer 失败时必须回复 BUSY，不能丢弃标识或阻塞持有分发名额。
- 容量满仍能接收 CLOSE/状态查询等请求，服务检查后按协议执行；普通客户端不能借控制操作绕过授权。一次即时处理有界，不同步等待远端。
- 已持有的请求通过 reply/rqfinish syscall 完成，取消/异步完成/IRQ 通过事件，不依赖再占普通 CALL 名额。
- 事件与消息交替；过载只明确拒绝新业务，不阻塞释放/收尾路径。恶意/故障服务不提供进展保证，管理者可隔离/终止。

验收：最小合法容量填满长请求，再排普通与 close/清理；后续控制取得进展，普通流量按 FIFO 被处理或明确拒绝，不无限自旋重试。

### exec 后的请求上下文（已确定方向）

PID保持的exec另有内部镜像代次，Rq调用/接收上下文及服务连接生命周期须保存对应代次；不能仅按PID认为旧等待、授权端点和新现场相同。具体保留fd与重建连接的提交规则随exec协议冻结。
旧镜像请求不恢复新寄存器、不使用同VA新缓冲，转交旧上下文收尾；新镜像不能用复制/猜测的旧RPC接管其结果。服务自身exec的旧入口发布也须明确失效，不能让新程序误收旧协议请求。

## 首版IPC数值与回收规格（已冻结）

Msg=4*u64/32字节，不增Endpoint/公开OP。文件协议在四个业务字中显式携带connid，建立连接等无槽消息按10定义解释；内核不解析该connid/token，也不增加IPC寄存器或消息字。调用号、kind、所有选项位及56字节Resreply见06，t0/x9来源image输出正式采用。queue/owned侵入链在192字节Rq槽内，queue只含QUEUED、owned只含ACCEPTED或终结但未server_finished者。TERMINAL=3、QUEUED=1、ACCEPTED=2；DRAINING由TERMINAL且!server_finished推导，不再设平行枚举。

终结位caller_consumed=1、server_finished=2、caller_released=4；另有queued/owned/同步临时引用，三完成位齐仍不能在任何临时引用存在时复用。Rq槽代次跨复用递增，REQUEST/RPC类别不同但同槽代次；调用者和服务的完整PID/image分别验证。所有路径唯一终结；中断后正常reply仍交付原结果，机制强制终结后的晚reply才只完成真实收尾。send无公开Handle且交付时即server_finished；同步call正常返回由内核代消费/释放；异步调用者显式ack；中断后原结果领取/强制终结收尾由libsys独立记录持有。

每进程12出站：普通8、信号层各1共2、控制/清理2。默认defer上限15并保留1即时名额；服务主循环每批最多32项，取消/观察/完成待处理游标未清空不能再次睡眠。控制关闭、取消、ACK使用既有保底名额，允许拒绝新业务而不封闭清理。计费在create预付，不在handler/退出临时找Rq。

运行中回复交付：CALL_RECV_MEM=2与CALL_RECV_CALL=4互斥，可与ASYNC=1组合；预留一个接收资源槽，普通call不预留。同意接收资源的CALL优先使用本镜像预付保底空槽，耗尽后才取普通空槽，不能将父本地槽当接收方；QUEUED取消、机制强制终结或普通回复将槽归还原保底/普通来源，ACCEPTED协作取消不归还，资源安装后转普通占槽，未用保底留至镜像结束。fork/exec/spawn按需接入不要求启动完成syscall或发布后期限，具体见08。Resreply.source要求源GRANT且目标种类符合显式同意；MEM仅SHARED/READ或READ|WRITE、页对齐子范围，不含EXEC/SEAL/DMA/再次GRANT；CALL仅USE，不含GRANT。offset/length对CALL为0。reply资源成功以kind=4及words[0]安装结果，3字业务元数据；reply_recv/send不支持交付。QUEUED取消或机制强制终结不安装；ACCEPTED协作取消保留槽，资源reply仍可交付实际结果。资源reply先提交安装引用归调用者，不再被Rq回收，查询不重复安装，libsys稳定记录后才ack。

资源reply已经提交后，同seq的新请求不得再次交付资源；调用者从原RPC/稳定返回现场恢复，仍持有同次token/连接对象时，服务只普通回复EALREADY/当前对象阶段，不能缓存或猜接收方本地Handle来重发资源。只有原Rq给出保证未执行的QUEUED取消或业务零效果EINTR，且旧准备补偿结束，才可用新seq重新建立；不得为取回结果重发同一建立业务。

共享同步和CPU内存顺序：生产方先写payload，release发布槽状态/序号；服务acquire后快照并核验，再访问。服务release发布结果/数据，reply承诺停止本次槽访问；调用者acquire后消费。设备DMA另走09同步，不把普通release当缓存维护。共享可被恶意对端修改，服务的控制参数读入私有有界快照，不能校验一次后继续信任共享控制字段。

原生IPC不自动SA_RESTART。rqwait中断不取消原请求；同步call中断同样只退出等待并返回原RPC。handler显式ack/release外层RPC后，原等待已保存结果快照可以正常交付，但不能再凭失效Handle查询/复用槽；运行库私有Handle不导出给应用当自主管理资源，若应用破坏内部记录则明确接口错误而非重建同值。服务已接收CALL时handler再次recv仍BUSY，外层成功接收结果不得被覆盖。

实际结果的短回复只固定在原Rq；大数据在原共享槽保持到调用者复制/保存，内核不保存第二份业务数据。服务只保留执行中状态及安全收尾责任，reply后释放自身操作记录，不保留等RESULT_ACK的结果表。跨新Rq重发业务视为新操作，库禁止据中断/丢提示重发；原请求存活时查询原RPC，服务失效结果未知则EIO，不盲目重做。文件层的RESULT/RESULT_ACK/CANCEL操作已删除，准备ABORT及内核rqcancel/rqack保留各自责任。

### 可信Rq机制执行切片（2026-11-16）

已落include/abi/ipc.h的32字节Msg及既定常量。include/list.h提供独立节点初始化、判空、头尾插入、摘除、移动和安全摘除遍历，检查插入/摘除关系。Rq实际184字节（上限192），默认1024槽共188416字节；记录只持稳定身份、精确来源Handle快照及双方Image引用，不存用户/C续点指针，queue/owned使用独立节点。

每进程构造预付12槽，按8/1/1/2隔离；普通准入只用前960槽，尾64槽保留恢复，选择恢复预算是可信内核输入。RQ提交不分配页。代次受43位Handle上限约束；回收要求三完成位齐、临时引用为0、两节点独立。存活所有者完成后回自己的空闲预付槽，关闭所有者的旧请求收尾后才归全局。Rquota为48、Rmail为64，均计入Proc，实际Proc496仍在512上限内；后续字段须通过阶段互斥复用/去重保持预算，不另开影子表绕过。
