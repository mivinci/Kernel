# 016 启动包缺少原子更新与回滚

状态：待处理　优先级：P1　关联：07#启动包与根目录、01、003

## 现象

启动包是单槽的：更新等于覆盖写同一位置。没有任何版本标识、代次记录或回退路径。基础服务（`init`/`serial`/`tty`/`blk`/`fs`）与救援 sh 都在包内且只读常驻，因此**改任一基础服务都要整包重刷**；这一粒度无法避免，因为挂载根目录所需的 `blk`/`fs` 不能放在根目录上，救援通道也必须随包可用。

## 影响

- 现场更新一次断电即可能得到半写包，设备无法启动，且没有第二个可回退的副本。
- 无法判断当前运行的是哪一版包，排障时无从对照。
- 与 003（板端自证）叠加：真机无 QMP 观测时，更新失败表现为"黑屏 + 无输出"。

## 建议方案

**A/B 双槽**，把"重刷"从危险动作降为可回退动作：

1. 存储上保留两个包槽；引导器按"当前有效槽"选择并把该范围经 DTB `/chosen` 或固定装载地址交给内核。
2. 包头用现有 `reserved` 字段记录 `slot` 与 `generation`，**不改格式版本、不改已冻结的字段布局**。
3. 更新流程：写备用槽 → 用现有 `bootpkg.check()` 做全量校验（magic/format/machine/count/FNV-1a64/区间不重叠/ELF 头）→ 切换引导器选择 → 启动失败则回退到原槽。
4. 内核零改动：它只校验包，不关心槽位；槽位选择属于引导器职责。

**包体控制**（配合本条，不单独立项）：

- 包内只保留"启动必需 + 救援必需"：`init`、`serial`、`tty`、`blk`、`fs`、救援 sh。当前默认包 4 项，上限 32，余量足够，但不应把通用工具塞进包。
- **不引入压缩**。包体只有数 MB，重刷时间不是瓶颈；压缩会破坏"零解析、原位只读"这一优点。
- **不做盘上热替换基础服务**：`fs` 持有挂载状态、`blk` 有在途 I/O，无损交接的复杂度远大于收益。

## 验收

- 半写或被截断的包在装载前被拒，不会进入用户态。
- 写入备用槽并切换后正常启动；把备用槽数据破坏后，回退到原槽仍能启动。
- 包头 `generation` 与实际部署版本一致，可从运行中的系统读出。
- 真机侧需硬件配合完成（引导器配置、掉电演练），本地只能验证到"包校验 + 选择逻辑"；**不得以本地通过代替上板结论**（003）。

## 备注

- 本条是"接受重刷粒度"的对策，不是消除重刷；理由是基础服务集合不可约。
- 槽位数量、引导器选择方式与掉电时序留待与 01/07 一并冻结，不在本条预设实现细节。
